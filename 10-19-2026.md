# System Software Software Thrust and Controls Meeting Minutes

**Meeting minutes \| October 19, 2026 \| 1 hour 18 minutes**

**Purpose.** Discuss a stack-wide integration plan, identify meaningful end-to-end workflows for the QSC testbeds, and clarify the compiler, runtime, QPU, and decoder boundaries needed to demonstrate a quantum error-correction (QEC) loop.

**Participants**: Amir Shehata, Narasinga Rao Miniskar, Seth Johnson, Christopher Zimmer, Travis Humble, and Jack Lange.

**Note on timing**: The transcript records the meeting as starting at 7:02 PM on October 19, 2026, and lasting 1 hour 18 minutes 30 seconds.

# Executive summary

The group supported planning integration around complete, purpose-driven workflows rather than simply connecting components. QEC was identified as the leading use case, with logical error rate and state lifetime among possible demonstration outcomes. The exact workload, hardware path, and performance measures remain to be selected. Participants agreed to meet again the following week and prepare an end-to-end view of the current compiler and execution pipeline, including its tasks, exchanged data, runtime responsibilities, and QEC components.

The discussion also reinforced a modular openQSE direction: workflow, compiler, circuit cutting, execution, decoding, and post-processing should be separable components with defined interfaces, so implementations can be replaced or combined across environments. The initial design should be a practical exemplar that can evolve into interface requirements and, later, specifications.

# Discussion

## 1. Stack-wide integration milestones and deployment

Amir proposed defining integration milestones across the full software and hardware stack. The intent is to understand how layers affect one another, identify the components that must be integrated, and specify the interfaces and requirements needed for them to work together. A current example is that compilers may need calibration or other hardware information through a quantum resource interface; the required information and access path are not yet fully specified.

A second integration mismatch concerns QIRIS. It currently accesses QDMI directly, while the IQM testbed is moving toward a service on the adjacent Dell system that uses QRMI or QDMI behind a unified QRI. Client components would call the QRI, which would invoke the selected device interface. The intended direction is for QRMI and QDMI implementations to conform to that unified interface, allowing the backend to be switched without changing clients. Existing token/base-URL access remains available during current integration testing, but components will need to adapt as the service-based deployment becomes the standard path.

The deployment concept has two related forms: a containerized SLURM environment that brings together the tools for users to clone and build, and a real-hardware deployment. The containerized cluster should resemble Janus closely enough to support reproducible experimentation. The Poughkeepsie testbed, now referred to as Umbra, is expected to be incorporated into the existing Janus One SLURM infrastructure, enabling allocations that span a Janus node and an Umbra node.

## 2. Define integration around workflows and use cases

Travis emphasized that component integration becomes a meaningful milestone when it supports a specific end-to-end purpose. The group should identify use cases or workflow patterns, describe the complete vertical stack for each, and track how many such workflows are supported. This approach makes the integration strategy concrete and prevents the team from connecting components without knowing what the combined system is intended to do.

QEC emerged as the preferred first use case because it exercises the fault-tolerant stack and responds to concerns that demonstrations based only on NISQ workloads may not show the requirements of future systems. A sampling-based quantum algorithm was mentioned as a possible second workflow, but it is less integrated with this group at present.

Potential QEC demonstration targets discussed included IQM, IBM, and the Clifford+T simulator (referred to in the transcript as â€œCliftâ€ or â€œCliff Tâ€). IBM integration remains uncertain, including how much of a QEC pipeline can be connected given firewall and network constraints. Pathfinder was considered less likely for the initial effort. A QSC-supported simulator path may offer an earlier way to explore circuits, although useful demonstrations depend on extending the simulator and adding decoder-loop and feed-forward capabilities. Those capabilities are still in development, and simulation scale is constrained, especially when feed-forward creates branching.

Participants discussed a potential space-time encoding or quantum-memory-style workload with IBM and AMD. The intended scientific result could be a comparison of encoded and unencoded state fidelity or lifetime. ## 3. Demonstration outcomes and candidate metrics

The demonstration should report both scientific outcomes and systems requirements. Logical error rate (LER) was identified as a likely headline result for a QEC demonstration. For a state-preparation or memory experiment, the lifetime of the encoded state and its fidelity may also be relevant. The systems team will also want to measure the resources required and the computational load. The exact metrics depend on the selected workload and should be agreed once the circuit and experimental objective are known.

The group considered whether a small end-to-end workflow could be run before the more capable simulator or full QEC integration is ready. A memory-style circuit without feed-forward may be feasible; some hand-encoded demonstrations have already been performed. The missing integration value would be to run a compiler-produced circuit through the workflow and connect resource allocation, compilation, execution, and result handling rather than demonstrating each piece in isolation. For a superconducting QEC workflow, the group noted that decoding on a CPU alone would not represent a time-sensitive real-time decoder; Riverlane or another suitable decoding framework may be more relevant.

## 4. Compiler and runtime responsibilities

The group worked through a preliminary workflow boundary. A workflow manager would create the workflow and use SLURM to reserve resources. An application runtime would prepare the application and configure a compiler pipeline for the selected hardware. The compiler would transform an input circuit through the required passes and emit a hardware-ready representation. An execution component would submit it to the QPU or simulator. Results may then pass to decoding and/or post-processing, including aggregation for workflows such as circuit cutting.

Narasinga described the current QIRIS-centered implementation as a set of tasks: circuit cutting, compilation, fragment execution, decoding, and result stitching can each be represented as work. The current examples run on a single node with the required CPU/GPU resources available there; distributed execution is being explored. The hardware-mapping path through the IQM compiler is currently used for Pathfinder and Emerald, while a complete hardware-mapping pass in the project compiler remains in progress. Current QDMI-based execution works for workflows that do not require the complete FTQC path.

Amir stressed that openQSE should support interoperable modules rather than require all functionality to live inside one framework. Circuit cutting, compilers, runtimes, execution services, decoders, and post-processing should be usable independently where possible. Narasinga confirmed that the compiler passes can be split and invoked as modules, and that the components are intended to be pluggable into runtime environments. Defining interfaces between these pieces remains necessary for interoperability across implementations.

Circuit cutting was discussed as an example of the modular flow: a compiler pass cuts a circuit into fragments, the fragments are compiled and executed, and a post-processing task combines the results. A two-cut example was described as producing 192 fragments. An FTQC compilation and decoding stage could be introduced for each fragment. This provides a concrete case for examining how task dependencies, resources, and results move through the stack.

## 5. Noise models, compilation, and feedback

The group discussed using device error models (DEMs) to configure decoders. These models may come from calibration data or be refined using an initial set of shots from the circuit to account for hardware drift. Because the calibration or training shots use the circuit and physical qubits of interest, they must be compiled and executed. Amir and Christopher agreed that this procedure belongs in the runtime or orchestration flow, while the compiler should remain a stateless component that receives a compilation request and returns a compiled circuit.

A key unresolved issue is where to draw the boundary between compilation, orchestration, and the QEC loop. Some correction paths may require branching or recompilation. Precompiling all branches is straightforward for a small example but may not scale. Just-in-time compilation could avoid that limitation, but current compiler passes reportedly take milliseconds, while some superconducting feedback requirements are below 10 microseconds. The group agreed that a workflow designed for a slower modality or a long-running simulator should not be assumed to satisfy tighter latency constraints.

The immediate goal is not to settle a general QEC specification. The group first needs a shared account of the existing pipeline and its sequence of operations. This should expose which components exchange information, what the runtime configures, and where the interfaces need to be clarified. More formal descriptions of QEC codes, decoder selection, and feed-forward protocols can follow as the exemplar is exercised.

## 6. QEC data flow and decoder orchestration

Mid-circuit measurement support requires coordination between the compiled physical circuit, the execution runtime, and the decoder. The runtime may need to start the QPU and decoder together, route syndrome data, and provide the decoder with the QEC code, operations, physical-qubit mapping, and measurement identities. The decoder identifies errors; the correction or branch choice is then applied through the compiled or subsequent circuit path.

For an initial design, Jack suggested treating decoder resources as statically provisioned alongside the QPU, which simplifies scheduling. Even with fixed infrastructure, the system must map decoder instances to code patches and establish data routes. The number and placement of decoder instances may depend on the circuit schedule. One decoder algorithm may have multiple instances working in parallel for different patches.

More complex codes, including QLDPC approaches where logical qubits or patches interact, may require dynamic routing of syndrome packets to decoder instances. Narasinga described an example in which a QPU sends syndrome data over 100 Gb Ethernet to an FPGA decoder, with destination information set so that packets reach the correct decoder. At tight real-time latencies, runtime orchestration cannot intervene for each packet; instead, runtime/compiler setup establishes the data flow and routes before execution, after which the data moves directly between components. The compilation stage may know in advance which measurements map to which decoders.

The diagram shown during the meeting did not yet include all setup and orchestration responsibilities. The group agreed that the next version should show an end-to-end QEC view, including resource setup, QPU and decoder placement, data routing, measurements, decoding, and feed-forward/correction. The diagram and sequence should be reviewed at the next meeting.

# Agreements and conclusions

- Plan integration milestones around complete, purpose-defined workflows and their end-to-end component stacks.

- Use QEC as the leading candidate workflow; retain sampling-based algorithms as a possible later workflow.

- Develop a shared description of the current compiler-to-execution pipeline before trying to define detailed specifications.

- Keep the compiler, runtime/orchestration, execution, decoder, and post-processing roles visible as separate components, with interfaces that can support substitution and interoperability.

- Treat calibration/noise-model acquisition and initial-shot refinement as runtime or orchestration concerns to be coordinated with compilation and execution.

- Continue the discussion the following week. The next iteration should include a pipeline sequence and an updated end-to-end diagram that captures QEC setup and data flow.

# Open questions

- Which QEC workload is the best initial exemplar, and what experimental outcome will it demonstrate?

- Which target path is feasible first: IQM, IBM, the Clifford+T simulator, or a combination?

- What access to IBM and AMD hardware/control interfaces is available, and what role should Umbra play?

- Which metrics should be reported beyond logical error rate, including state lifetime/fidelity, decoder latency, and resource use?

- What information must pass among compiler, runtime, QPU, decoder, and workflow manager, including code descriptions, physical mappings, measurement identities, and feed-forward decisions?

- How will the system support mid-circuit measurements, decoder selection, decoder-instance mapping, and routing of syndrome data?

- Where is the boundary between precompiled branches and just-in-time compilation, given the gap between current millisecond compiler times and microsecond feedback requirements?

- What module contracts will allow QIRIS functions, alternative compilers, cutting methods, decoders, and post-processing tools to interoperate?
