# 06. The QEC execution loop

All participants are configured and armed before this sequence starts. Controller and decoder exchange data directly; the workflow engine, Slurm, and ordinary host RPC path do not process each QEC round. A measured check bit, a syndrome value, and a detection event derived across rounds are not automatically the same representation. The configured schema assigns that transformation to a specific component.

Riverlane reports a Qblox–Deltaflow hardware loop over LINQ/QECi, including conditional correction, using emulated measurement input rather than live qubits. This supports the example transport path, not a claim about the testbed's live-qubit performance. [Riverlane integration report](https://www.riverlane.com/blog/riverlane-and-qblox-have-closed-a-full-real-time-qec-loop).

```mermaid
sequenceDiagram
    autonumber
    participant DR as Device Runtime
    participant CT as QPU Control
    participant QP as QPU
    participant DE as Decoder
    participant TX as Telemetry Export

    DR->>CT: Start armed program and configuration epoch
    loop Shots and repeated QEC rounds
        CT->>QP: Execute encoded operations and stabilizer extraction
        QP-->>CT: Ancilla readout signals
        CT->>CT: Discriminate and label measurements
        CT->>DE: Ordered stream with shot, round, patch, and epoch identity
        DE->>DE: Form detection events if assigned here; update decoding state
        opt A decision is required at this feedback boundary
            DE-->>CT: Frame delta, logical decision, or correction with identity
            CT->>CT: Validate epoch, ordering, and deadline
            alt Software/control frame update suffices
                CT->>CT: Update authoritative frame or interpret next operation
            else Compiled conditional physical action required
                CT->>QP: Execute prepared correction or branch
            end
        end
        opt Configured nonblocking capture is supported
            CT-->>TX: Measurement copy and timing
            DE-->>TX: Decode/frame copy and timing
        end
        CT->>QP: Reset ancillas as compiled and continue
    end
    CT->>QP: Final logical readout sequence
    QP-->>CT: Final physical measurements
    CT->>DE: Final records and end-of-shot/run markers
    DE-->>CT: Final frame or logical observable interpretation
    CT-->>DR: Results, final frame reference, and deadline/error counters
```

The controller is shown as frame owner for this variant. Another design may keep the authoritative frame in the decoder/runtime, but must define a single owner and how frame-dependent operations consume it. Many memory/Clifford rounds permit deferred corrections; they do not require a physical correction after every measurement round. Non-Clifford operations or logical measurements can create decision deadlines. Decoder throughput must keep pace with incoming work even when decision latency spans several rounds.

## Open questions

- **Representation:** Are transported records raw thresholded bits, syndrome parities, detection events, soft information, or leakage flags? Who transforms each representation?
- **Timing:** What is the round cadence, sustained throughput, worst-case decision latency, and actual feedback boundary? Decoder processing latency alone is not the full loop budget.
- **Frame:** Who owns frame state, and how are frame-dependent logical gates and final observables interpreted without applying a correction twice?
- **Streams:** How are missing, duplicated, reordered, late, and cross-epoch records detected? Can the system mark a shot invalid or abort deterministically?
- **Control:** Does the controller accept an arbitrary correction vector, a logical measurement bit, or only predefined conditional action IDs?
- **Availability:** Which parts are exposed on the actual QPU path, including repeated mid-circuit measurements and reset? A batch circuit API may not expose the required stream.
